# Night log, 24 to 25 Oct 2026: option 1, framework rebuilt with execute-from-PSRAM

Goal: rebuild the Arduino framework with CONFIG_SPIRAM_XIP_FROM_PSRAM (fetch instructions and
rodata from PSRAM) and CONFIG_LCD_RGB_ISR_IRAM_SAFE, so flash writes no longer stall the panel
refill, then prove it on the board with writes forced during motion. Logan is asleep; this
file is the hand-over if the session ends early. Newest entry at the bottom.

- 21:40 The hybrid build (pioarduino custom_sdkconfig) fails at the firmware.elf step with
  "ModuleNotFoundError: No module named 'SCons.Tool.FortranCommon'". The module imports fine
  from the installed tool-scons 4.11.1 under the PlatformIO Python, so the failing import runs
  in another interpreter or path. Re-running with SCONSFLAGS=--debug=stacktrace to get the
  traceback. Earlier attempts: 1 fetched ESP-IDF 5.5.5 and compiled the libs (152 s), 2 and 3
  failed in under a minute at the same step; the hybrid build also removed the scons tool once

- 21:50 Added a bench proxy for the defect, serial key Z: a 1 ms PSRAM-touching task records
  its longest stall while five event files are written. Prebuilt framework: the stall should
  equal the write time (cache off); with execute-from-PSRAM it should stay near 1 ms. The glass
  cannot be read back, so this is how the fix is judged without Logan's camera. Not yet built
  (the hybrid build holds the project lock).
- 22:05 Mechanism of the SCons failure found: the hybrid build replaces the tool-scons package
  mid-run with the version in the platform's platform.json (4.8.1) while the running SCons is
  4.11.1; the package directory vanishes and the link step's lazy import of
  SCons.Tool.FortranCommon fails. Each normal build then reinstalls 4.11.1. Workaround: a pre
  extra_script (firmware/tools/pre_scons_imports.py) imports the lazily used SCons tool
  modules before the swap. Rebuilding.
- 22:15 The pre-import did not help: the hybrid build deletes tool-scons at script load, before
  any extra_script runs (the package directory is empty afterwards and every normal build
  reinstalls 4.11.1). Next: pin tool-scons for the xip env to the same 4.11.1 tarball the core
  uses (platform_packages), so the reinstall is a no-op. Normal build first to restore the tool.
- 22:25 Pinning tool-scons did not stop the reinstall (same version, uninstalled and installed
  again at start-up), but it showed the real culprit: Python's import cache for the package
  path is stale after the reinstall, so any later import from it fails. The pre-script now
  calls importlib.invalidate_caches() before importing the SCons link helpers. Rebuilding.
- 22:40 Root cause of the tooling fault, from the platform's own code: for custom_sdkconfig
  builds the platform runs install_tool() on tool-scons. The installed package (4.41101.0, the
  version PlatformIO Core 6.2 runs on) fails its version check against the platform.json entry
  (4.40801.0), so the platform deletes the package directory to "reinstall" it, and then
  neither reinstall path applies (no tools.json, no .piopm), leaving no SCons on disk under
  the running interpreter. Workaround: edit the local platform.json so tool-scons expects
  4.41101.0 and the 4.11.1 tarball. This is a per-machine patch; noted in firmware/README.md.
